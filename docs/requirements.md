# Yomihime Game Link · 怜的游戏连结 — 需求文档

> 状态：需求整理稿，不代表功能已实现，也不是已定稿的技术方案。
> 整理日期：2026-09-13。
> 来源：用户在项目讨论中的明确要求，以及 AstrBot 整理的《AstrBot 游戏聚合查询插件 - 需求文档（v2.0 模块化版）》草案。
> 用户明确要求优先；原始草案中的架构、接口与扩展项是待评估提案，不视为执行指令。本文不将讨论中的建议自动记为已确认决策。

## 1. 已确认的定位与命名

- 英文名：**Yomihime Game Link**。
- 中文名：**怜的游戏连结**。
- 插件标识与仓库名：`astrbot_plugin_yomihime_game_link`。
- GitHub：<https://github.com/yomihime/astrbot_plugin_yomihime_game_link>，公开仓库。
- 定位：AstrBot 多游戏聚合信息查询插件，不限定于单个游戏。
- 首批明确需求涉及 Dota2 与 FF14，后续可扩展其他游戏。
- **Yomihime Arcade** 名称预留给未来的 Bot 聊天游戏项目；本项目聚焦信息查询和账号关联。

## 2. 核心用户需求

用户希望直接向 Bot 发送查询请求，获取指定游戏的信息；按聊天用户绑定游戏账号或角色后，后续说“我的战绩”“我的 Logs”等即可使用自己的绑定对象。

### 2.1 Dota2

- 查询指定对局的信息。
- 查询指定玩家的战绩。
- 将 Dota2 账号绑定到当前聊天用户。
- 未明确指定玩家时，可以查询当前用户绑定的账号。
- 英雄胜率等细分统计出现在原始草案中，具体统计范围待确认。

### 2.2 FF14

- 查询指定角色的 FFLogs 信息。
- 将 FF14 角色绑定到当前聊天用户。
- 后续查询“我的 Logs”等请求时，使用该用户绑定的角色。
- 角色资料、副本进度、DPS 统计来自原始草案；具体展示字段和首版范围待确认。
- 国服、国际服或同时支持两者尚未决定。

### 2.3 聊天交互

以下是意图示例，不是已经实现或定稿的命令语法：

| 用户表达 | 期望行为 |
| --- | --- |
| 查一下 Dota2 对局 1234567890 | 按对局 ID 查询详情 |
| 查这个 Dota2 玩家的战绩 | 使用用户明确提供的玩家标识查询 |
| 帮我绑定 Dota2 账号…… | 将该账号与消息发送者关联 |
| 查我最近的 Dota2 战绩 | 自动使用当前用户的 Dota2 绑定 |
| 绑定我的 FF14 角色…… | 保存角色与消息发送者的关联 |
| 查我的 FF14 Logs | 自动使用当前用户的 FF14 角色 |

“直接发送即可查询”和绑定后的自然语言查询是产品需求；是否使用 Function Calling、哪些请求用固定命令处理、无模型时如何回退属于待定实现方案。

## 3. 账号绑定：建议补齐的规则

以下是讨论中提出的设计建议，尚未逐项由用户确认：

- 聊天用户标识包含平台身份范围，避免不同平台的同号用户串绑。
- “我”从消息事件中的发送者身份解析，不由模型生成用户 ID。
- 支持查看绑定、解绑；是否允许每游戏多个账号及切换默认账号待确认。
- 查询对象优先使用明确指定的账号，否则读取当前用户该游戏的默认绑定。
- 未绑定时提示如何绑定，同时允许通过明确账号进行临时查询。
- FF14 角色保存足以消除重名歧义的信息，例如区域、服务器与角色标识。
- 区分“保存默认查询对象”与“验证账号归属”；绑定是否要求归属验证待确认。
- 同一用户跨群是否共享绑定、跨平台账号是否可以合并，需明确规则。
- 不同用户不能通过自然语言参数修改他人的绑定。

## 4. 原始草案中的架构提案

这些内容保留作为设计输入，不意味着必须按该目录结构或接口签名实施。

| 领域 | 原始提案 | 讨论后的待评估方向 |
| --- | --- | --- |
| 整体结构 | 核心框架 + 可插拔游戏模块 | 保留游戏模块边界，按实际需求逐步拆分 |
| 核心层 | 模块管理、统一存储、意图分发、标准接口 | 核心不包含具体游戏业务逻辑 |
| 绑定存储 | SQLite；用户、模块、账号、额外信息 | 补齐身份范围、默认账号规则和迁移设计 |
| 自然语言 | Function Calling 优先，关键词匹配兜底 | 与明确命令共用查询服务；不支持模型调用时的行为待定 |
| 模块加载 | 扫描目录、配置启停、独立热重载 | 首版建议配置启停，暂缓模块独立热重载 |
| 标准接口 | 模块名、命令列表、意图处理、初始化 | 命令描述与工具参数 schema 分开设计 |
| 返回结果 | `handle_intent(...) -> str` | 建议返回结构化数据，由展示层生成文本或图片 |
| 公共能力 | HTTP、缓存、限流、重试、格式化 | 按数据源需求设计，避免无需求的抽象 |
| 配置 | 独立 `config.yaml` | 实现前核对 AstrBot 插件配置机制 |

原草案提出的 `core/`、`modules/dota2/`、`modules/ff14/`、`shared/` 等是候选结构；当前仓库没有实现这些模块。

## 5. 数据源与语义边界

| 功能 | 候选数据源 | 实现前需要验证 |
| --- | --- | --- |
| Dota2 对局、战绩 | OpenDota API | 玩家标识转换、公开数据可用性、接口字段、配额与限流 |
| FF14 Logs | FFLogs API | 区域和服务器映射、角色定位、统计口径、认证与报告可见性 |
| FF14 静态资料 | XIVAPI | 所需静态资料及语言支持；不能默认视为完整角色查询来源 |
| FF14 角色定位 | 待定 | 国服与国际服覆盖、稳定角色标识、改名与转服行为 |

讨论中已查阅的资料：

- [FFLogs API 文档](https://www.fflogs.com/api/docs)：v2 使用 GraphQL；公开数据与私人报告的授权路径不同。保存角色绑定不等于取得私人报告访问权限。
- [XIVAPI v2 文档](https://v2.xivapi.com/docs/welcome/)：主要提供游戏静态数据，角色查询需要单独确认来源。
- [AstrBot 插件开发指南](https://docs.astrbot.app/dev/star/plugin-new.html)：插件元数据、运行时加载、重载与开发约定。

以上是规划参考，精确接口、配额、覆盖范围和版本兼容性需要在接入前重新核验。

若展示“副本进度”，需要明确它表示 Logs 中可见的记录，不能直接推断为完整游戏内进度。DPS、排名、百分位等应明确副本、难度、职业、分区或版本及统计口径；具体默认值待定。

## 6. 后续扩展候选

以下项目来自原始草案，用户尚未确认进入首版或承诺具体交付时间：

- **游戏价格**：当前价格、历史低价、折扣提醒；候选来源包括 Steam、IsThereAnyDeal、小黑盒。
- **新闻聚合**：更新日志、游戏新闻；候选来源包括 Steam News、媒体 RSS。
- **图鉴检索**：角色、技能、物品的模糊查询；草案举例为死锁、炽焰天穹，候选方案为本地 JSON 或向量索引。
- **更多游戏**：以独立模块扩展，具体名单按实际需求确定。

爬虫、IP 轮换、向量索引、主动推送均不作为当前已确认需求。数据获取方式和提醒订阅机制如需实现，另行设计。

## 7. 建议的质量与异常处理要求

- 区分对象不存在、尚未绑定、数据未公开、无记录、接口限流和上游故障。
- 模块错误不得导致整个插件不可用；返回可理解的错误信息。
- 使用异步网络请求，设置超时，按上游响应实行有界重试与限流。
- 按数据源与查询类型设计缓存；不能仅假定所有查询都是 GET 请求。
- 缓存需要隔离授权范围，避免向其他用户返回私人数据。
- 展示结果时保留来源；使用缓存时提供必要的更新时间信息。
- 账号与其他持久化数据放在 AstrBot 数据目录，不随插件源码更新覆盖。
- 凭据通过部署配置管理，不提交到仓库，也不回显在消息或日志中。

本节为实现时待细化的验收建议，不代表已有对应能力。

## 9. 建议的实施顺序（待定稿）

| 阶段 | 建议交付 | 建议验收 |
| --- | --- | --- |
| M1：最小 Dota2 查询 | 明确账号战绩与对局查询，确定数据模型 | 指定对象有结果，限流、无记录等反馈准确 |
| M2：用户绑定 | 保存、读取、查看、解绑；若确认则增加多账号与默认账号 | 用户互不串绑，重启后绑定仍存在，解绑后不再隐式使用 |
| M3：自然语言入口 | 将“我的战绩”等请求接入同一查询服务 | 正确使用消息发送者的绑定，歧义和缺失参数有明确反馈 |
| M4：FF14 接入 | 按确认的区域支持角色绑定与 Logs 查询 | 同名角色可区分，统计口径明确，多游戏绑定互不覆盖 |
| M5：扩展 | 按后续需求接入价格、新闻、图鉴等 | 每项单独定义验收，不默认全部开发 |

这是一份便于后续讨论的排序，不替代正式开发计划。开始实现前应细化接口、依赖、提交分组与部署验收方法。
