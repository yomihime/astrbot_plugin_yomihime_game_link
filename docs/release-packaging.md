# 完整安装包

Core 与 DLC 通过 `ygl.control/1`、`module_contract 2.0` 和版本化 features 协商。Core 0.2.8 起支持普通安装格式；Steam DLC 0.3.1 起默认生成该格式。私有 SDK 随 Core 安装，普通安装无需另装 pip wheel。

## 普通安装和更新

在各自仓库运行：

```sh
# Core
python scripts/build_release.py --output-dir <build-dir>

# DLC
python scripts/build_release.py --output <build-dir>/plugin.zip
```

在 AstrBot 的插件管理页上传并启用完整 ZIP。更新时使用同一入口。Core 与扩展可以分别安装，兼容的扩展会在 Core 就绪后自动接入。普通包无需额外审批。DLC 的 `--allow-dirty` 仅用于允许未提交源码的本地构建。构建记录会标明实际源码状态。

默认清单采用 `ygl.release/2`，字段为 `schema`、`plugin_id`、`package_id`、`release`、`payload_digest` 和 `files`，不包含签名、公钥、渠道或发行序号。文件清单仍严格覆盖包内载荷，并核对路径、大小和 SHA256；运行时验证 Host 当前安装身份、启用状态、版本、SDK 及数据兼容性。业务权限、来源限制、凭据授权和发送权限继续独立检查。

每包严格小于 16,000,000 字节；解压大小、单文件和文件数量还受运行时预算限制。`BUILD.json` 记录源码提交、未提交状态及来源摘要；`SHA256SUMS` 记录完整 ZIP 的摘要。内容摘要识别具体字节，不代表外部发布者身份认证。

AstrBot 市场的 `download_url` 应指向完整且不可变的安装 ZIP，不能指向缺少生成清单及静态资产的自动源码归档。Actions 下载需先解开外层工件 ZIP。版本号决定市场是否显示更新；同一版本的新字节可以通过正常 ZIP 重装更新。

兼容更新通过旧运行代停止、准备新运行代、核对当前 Host 实例后切换，不要求整个 Host 重启。共享依赖或原生库变更属于环境维护。旧 SDK 版本首次迁移可能需要一次重启；正常后续更新无需重复重启。安装成功提示不等于业务已就绪，应同时核对 Core Ready、DLC 状态以及已安装与运行摘要。

配置、绑定、订阅、凭据和数据库继续使用现有数据。更新前保留一致备份，不清库或重新生成业务密钥。普通安装遵循 Host 所选版本，但仍执行数据兼容性检查；不要假定旧代码能够读取升级后的数据库。普通 DLC 校验或启动失败时会明确报错，不会自动改跑缓存旧包；请核对状态后重新安装兼容的完整包，保留现有数据。Core 自身在新安装通过验证后，可按身份与迁移兼容条件使用已记录的精确 current/last-good 包恢复。缓存孤儿目录不能作为已接纳包运行，恢复不会覆盖数据库。

## 旧签名格式兼容

显式传入 `--signing-key <external-key.pem>` 或开发用 `--test-signing` 时，构建器继续生成 `ygl.release/1`。`--channel` 和 `--sequence` 仅用于这条兼容路径；签名构建默认 `preview`、序号 `1`，测试签名只允许 preview。普通安装不使用这些参数。

旧格式保持原有 Ed25519 签名、发布者、包批准、无签名精确摘要批准和发行头校验。不能把旧包的损坏签名解释成普通包，也不能用相同发行序号签发不同内容。Core 包内公钥校验用于该旧安装流的完整性与连续性，不是独立于管理员所选 ZIP 的信任根。私钥不得加入安装包。

普通格式不依赖或改写旧批准及发行头记录。旧格式 DLC 未通过接纳校验时也会明确拒绝；只有已接纳后的运行失败才可尝试旧格式的精确缓存恢复，且仍须通过身份、签名、批准和数据兼容检查。Core 跨格式内部恢复还须满足插件身份和迁移清单兼容。保留历史与恢复材料，不删除记录来规避旧格式约束。
